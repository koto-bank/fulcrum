* Build
Generate:
~rm -rf _build ; mkdir _build ; cmake . -B _build -DCMAKE_EXPORT_COMPILE_COMMANDS=1~

If you want to use some other compiler, e.g. clang, pass these options
to cmake: ~-DCMAKE_CXX_COMPILER=clang++ -DCMAKE_C_COMPILER=clang~

Build:
~cmake --build _build~

** Not the freshest Linux distro
Take for example Ubuntu 22, which has the following issues:
1. llvm in package manager is very outdated
2. C++ compiler is also quite outdated, and doesn't support
   e.g. std::expected

The 1st problem can be solved by llvm provided script to install fresh
version:

~sudo bash -c "$(wget -O - https://apt.llvm.org/llvm.sh)"~

Ah, the safe and reliable wget2sudo, my beloved.

The 2nd one is partially solved by the 1st step leaving us with a
modern clang, but there's also an issue of libstdc++ expecting
different language macro values than libc++ would have, specifically,
we need ~__cpp_concepts~ to be defined with value >=202002L in order
for std::expected to work. Thus, to correctly configure Fulcrum for
building, the following CMake command shall be used:
#+begin_src
cmake . -B _build -DCMAKE_EXPORT_COMPILE_COMMANDS=1
-DCMAKE_CXX_COMPILER=clang++-18 -DCMAKE_C_COMPILER=clang-18
-DCMAKE_CXX_FLAGS="-D__cpp_concepts=202412L
-Wno-builtin-macro-redefined" -DLLVM_CONFIG_BIN=llvm-config-18
#+end_src

* Using Fulcrum from CMake
Fulcrum is available to CMake as a first-class language, so ~.fc~ files can be
compiled, archived, linked and installed by ordinary CMake commands.

** From an installed Fulcrum
#+begin_src
cmake_minimum_required(VERSION 3.25)

# C must be enabled before Fulcrum, see "The C requirement" below.
project(myapp LANGUAGES C)

find_package(Fulcrum REQUIRED)
enable_language(Fulcrum)

add_executable(myapp main.fc)
add_library(mylib SHARED mylib.fc)
#+end_src

Point CMake at the installed package with ~-DCMAKE_PREFIX_PATH=<prefix>~, or at
an uninstalled Fulcrum build tree with ~-DFulcrum_ROOT=<build dir>~.

~find_package(Fulcrum)~ sets ~CMAKE_MODULE_PATH~, which is directory-scoped, so
call it in the same directory as ~enable_language(Fulcrum)~ or in a parent of
it, and before any ~add_subdirectory()~ that needs Fulcrum.

** Without find_package
If the language modules in ~cmake/~ are already on ~CMAKE_MODULE_PATH~, the
compiler is located, in order of precedence, from:
1. the ~CMAKE_Fulcrum_COMPILER~ cache variable (~-DCMAKE_Fulcrum_COMPILER=...~,
   or a toolchain file)
2. the ~FULCRUM_COMPILER~ environment variable
3. a ~fulcrum~ executable on ~PATH~

** Source file extensions
~.fc~ and ~.fulcrum~. Anything else needs an explicit
~set_source_files_properties(x.foo PROPERTIES LANGUAGE Fulcrum)~.

** The C requirement
~fulcrum~ emits relocatable object files and cannot link, so CMake drives every
Fulcrum link step through the C compiler driver. Enabling Fulcrum without C is a
hard error. Enabling C also gives Fulcrum the system include directories it
needs to resolve ~(import :c "stdio.h")~, which it gets from
~CMAKE_C_IMPLICIT_INCLUDE_DIRECTORIES~ -- so a C import needs no manual ~-I~.

** Supported generators
~Ninja~, ~Ninja Multi-Config~ and ~Unix Makefiles~. The IDE generators have no
code path for a custom language.

** Known limitations
- *One ~.fc~ file per target.* Fulcrum has no forward declarations, and
  ~(import other-module)~ copies function bodies into the importer under a
  ~nick:name~ symbol, so Fulcrum modules cannot yet call each other across
  object files. A Fulcrum library is consumable from C and C++, which see its
  plain unmangled symbols; see ~examples/hello~.
- *~target_compile_definitions~ is silently ignored* on Fulcrum sources.
  ~fulcrum~ has no ~-D~ switch, so the ~<DEFINES>~ placeholder is deliberately
  absent from the compile rule.
- *No dependency tracking.* ~fulcrum~ emits no depfile, so editing an imported
  module or an imported C header does not rebuild dependents. Use
  ~set_source_files_properties(x.fc PROPERTIES OBJECT_DEPENDS ...)~ meanwhile.
- *~CMAKE_BUILD_TYPE~ does not affect Fulcrum sources.* There is no ~-O<n>~ and
  no ~-g~, so all configurations produce identical objects.
- *Host only.* The target triple is always
  ~llvm::sys::getDefaultTargetTriple()~, so cross-compiling silently produces
  host objects.
- *Always position independent.* The compile rule passes ~--pic~
  unconditionally, because the host C driver defaults to ~-pie~ and a non-PIC
  object cannot be linked into an executable. ~fulcrum~ has no switch to ask
  for the static relocation model back.
- The language modules use CMake's internal, unversioned language API, so a new
  CMake release can break them. The ~fulcrum-examples~ test is the canary.

** Compiler flags CMake relies on
~-o <file>~, ~-I <dir>~, ~--pic~ and ~--version~. Also useful by hand:
~--emit-llvm~ dumps the generated IR to stderr, and ~-v~ raises the log level to
debug.

* Debugging
** LLVM and Clang
If you want to have llvm and clang debug symbols, and you most
certainly want them, you should compile llvm and then set environment
variables LLVM_DIR and Clang_DIR to appropriate locations.

*** How to compile LLVM and Clang
In llvm dir (tested on version 19.6):
#+begin_src
mkdir _build llvm-install
cd llvm
cmake -B ../_build -DCMAKE_BUILD_TYPE=Debug \
                   -DCMAKE_INSTALL_PREFIX=../llvm-install \
                   -DCMAKE_C_COMPILER=clang \
                   -DCMAKE_CXX_COMPILER=clang++ \
                   -DCMAKE_CXX_FLAGS=-glldb \
                   -DBUILD_SHARED_LIBS=ON \
                   -DLLVM_BUILD_EXAMPLES=OFF \
                   -DLLVM_ENABLE_ASSERTIONS=ON \
                   -DLLVM_ENABLE_PIC=ON \
                   -DLLVM_ENABLE_RTTI=ON \
                   -DLLVM_ENABLE_PROJECTS="clang;lldb" \
                   -DLLVM_TARGETS_TO_BUILD=host
cmake --build ../_build
cmake --build ../_build --target install
#+end_src

ENABLE_PIC and BUILD_SHARED_LIBS options are important. (Or one of them
anyway). Failure to provide them on generation step can lead to ld being unable
to link Clang libraries with Fulcrum.

After completing the steps, the installed llvm will be in ./llvm-install
directory, and can be used during fulcrum build by setting ~LLVM_DIR~ and
~Clang_DIR~ as explained above.

The ~-glldb~ option is needed if you want to debug the resulting executable with
lldb. Otherwise it will be unpleasant: incomplete types, failures to find
certain symbols and so on. If you build with gcc, change the argument
accordingly, to ~-ggdb~.

** Parser
There's ~Parser::Expression::dump()~ method, which is intended to be
used in situations where there's a need to inspect AST more closely.
Use it like this:
#+begin_src
bool SemanticAnalyzer::run(Parser &_parser) {
    parser = &_parser;

    auto tree = parser->releaseSyntaxTree();
+    tree->dump();
#+end_src

* Language
** Module declaration
*** Syntax
#+begin_src
(module module-name
   (import some-module)
   (import :c "stdio.h")
   (import :c "SDL2/SDL.h"))
   (import other-module :as nickname)
#+end_src

Imports with nicknames are imported as ~nickname.symbol_name~.
Imports without nicknames are prefixed as module name.

Names from C imports are imported directly inside the module.

** Function definitions
#+begin_src
(fn function-name ret-type ((arg-1 arg-1-type) (arg-2 arg-2-type))
fn-body)
#+end_src

** Variable declaration
#+begin_src
(var name type [initial value])
#+end_src
